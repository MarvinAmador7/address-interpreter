# Library review and MLS corpus evaluation

This is the initial review and round-two snapshot. The subsequent parser research and expanded sample are recorded in the [400,000-address report](research-400k-2026-09-26.md). Values labeled current below refer to that earlier snapshot.

Reviewed 2026-09-26 against baseline commit `272ca49`. Changes are local and have not been published. This report covers the complete source, public types, resolver contract, tests, package exports, dependency audit, CI, and documentation. Two independent review passes checked the implementation and API contract. All actionable findings from those passes were corrected and regression-tested.

## Findings and changes

| Area | Finding in the baseline | Implemented change |
| --- | --- | --- |
| Delivery model | Every input had to start with a house number. Postal forms could not be represented. | Separate PO-box, rural-route, highway-contract, military-box and General Delivery grammars with explicit kinds and their own fields/spans. |
| Primary number | One token became the house number if it contained any digit. Fractions were split into street names, while malformed punctuation was accepted. | Token-shape validation; fractional glyphs and multi-token fractions; alphanumeric and compound grid numbers; hyphen/slash ranges; competing readings for separated numeric ranges. |
| Street grammar | Literal, explicit-unit and bare-unit paths repeated directional/suffix parsing and disagreed on names such as `North Ave`. | Shared street parsing plus alternatives for registered directional names and suffix/name collisions. No directional alternative can repeat a consumed word. |
| Bare units | Required a digit and a preceding suffix. Alphabetic units and suffixless-street units were missing. | Letter-only, alphanumeric, hyphen/slash and suffixless bare-unit candidates. The street reading remains available. |
| MLS feed formatting | Repeated suffixes, abbreviated highway names, joined markers such as `Apt4`, and spaced house ranges hid components. | A bounded additional token reading and explicit alternatives preserve original interpretations, source offsets, identifier punctuation, and repair assumptions. Multi-token bare units and letter/number spacing alternatives retain complete secondary chains. |
| Secondary components | Building/apartment chains became one opaque identifier; `Apt #4` retained the extra hash. | Ordered `secondaryUnits`, individual spans, normalized redundant hashes, named identifiers such as `PH`, compound attached hashes, and ordinal-first floors. |
| Vocabulary | The suffix table covered only a subset of USPS forms. | All 206 primary forms from Appendix C1 and their listed aliases, with canonical abbreviations mapping to themselves. Existing `CARR` support retained. |
| Locality | Attached commas were not token boundaries. Full-address enumeration could swallow apartment lines, invent cities from complete streets, and absorb explicit locality delimiters. | Delimiter-aware tokenization and prefix reuse, secondary-line handling, state/ZIP/country endings, urbanization lines, and guarded locality splits. City names that are also unit keywords remain valid candidates. |
| Evidence | Some candidate-ID constructions could collide when an equal span meant city versus state. | Full IDs include span field names. Tokens and spans always reference the original input, including after Unicode normalization. |
| Runtime input | Invalid JavaScript types threw despite the documented diagnostic contract. Large inputs generated unbounded work/candidate sets. | Runtime type checks, character/token/candidate budgets and fail-closed results on overflow, including nested interpretation paths. |
| Resolution | Unknown candidate IDs or empty entity IDs could resolve successfully. | Validate adapter evidence before identity grouping; propagate malformed adapter/infrastructure errors instead of reporting a match or miss. |
| Packaging | The CommonJS export selected ESM `.d.ts` declarations, causing TS1471 for Node16-style `.cts` consumers. | Conditional ESM/CJS type exports and tests against an actual packed tarball. |
| Dependencies | Initial npm audit reported four development-tool advisories. | Vitest 4.1.11 and lockfile fixes, including esbuild 0.27.2. Final npm audit reports zero advisories. There are still no runtime dependencies. |

The initial 126 tests passed. A first 49-case regression suite failed 45 cases before implementation. The first review finished with 212 tests. The feed-format follow-up reproduced 21 failures before implementation; the current suite has 238 tests, including 1,500 seeded inputs checked through both interpreters for determinism, raw-token fidelity, valid offsets, unique IDs and bounded candidate counts. Additional tests cover combined repairs, ambiguity against competing index entities, candidate exhaustion, malformed resolver evidence, and infrastructure errors.

## Live source and sampling

The HomeAnalytics MotherDuck connection succeeded. Schema inspection and extraction ran against the live `homeanalytics.raw.attom_listing_analytics_complete` national MLS source. No database tables, jobs, grants, or customer accounts were changed.

The downloader selected only address fields, sampled 1% of source blocks with seed `20260926`, deduplicated rows over the selected fields, and capped each disjoint address-shape category at 2,000 records. This deliberately oversamples difficult shapes and is not a representative random sample of US addresses. The category labels are sampling heuristics, not validated property classifications.

- Downloaded 20,214 records covering 20,109 property groups, all 50 states and DC.
- Included 1,601 building/suite records, 613 fraction/space-house records, and 2,000 records in each of the other nine categories.
- Assigned 16,158 records to development and 4,056 to holdout using a hash of property identity. There is zero property-group overlap.
- Scored 16,068 development and 4,033 holdout records. The remaining 113 records lack a reference house number or street name and were excluded from field-agreement scoring.
- The saved corpus is approximately 9 MB. No agent/owner/contact fields were selected.

Corpus SHA-256: `b8585e3aac38df9a7b06fc04093a677f40c846df6ccdd87def7e95bf73a2de87`.

The extract and address-level reports stay in `.local/corpus/`, which git ignores and the npm allowlist excludes. The extraction script and evaluation script are tracked source without credentials or downloaded address data. Synthetic regression examples use stand-in addresses for patterns found during development.

Parsing rules were selected from development examples. No holdout address-level failures were inspected. The follow-up reuses the existing holdout after its aggregate score had already been reported; it is a repeated comparison, not a newly blinded evaluation. Development review distinguished parser defects from truncated house numbers, incomplete unit markers, omitted units, and other source inconsistencies.

| Untouched MLS listing string, all address fields | 2,383/4,033 (59.088%) | 2,852/4,033 (70.717%) | 2,975/4,033 (73.766%) |
| Generated explicit unit line | 3,878/4,033 (96.157%) | 4,032/4,033 (99.975%) | 4,032/4,033 (99.975%) |

| Generated full address with locality | 3,878/4,033 (96.157%) | 4,032/4,033 (99.975%) | 4,032/4,033 (99.975%) |

The follow-up recovered 123 held-out MLS listing strings, a 3.050 percentage-point gain over the first review, and five generated bare-unit cases. It lost no previous match in any of the five scenarios. Development listing agreement rose from 11,278/16,068 (70.189%) to 11,781/16,068 (73.320%), recovering 503 cases. Development also gained four property-line cases and seven generated bare-unit cases, with zero regressions in any scenario. The evaluator, comparison fields, normalization reference and denominators were unchanged.

Average candidates per held-out listing increased from 1.57 to 1.67. More candidates mean more index work and possible ambiguity; these measurements establish candidate recall against source fields, not resolution precision. Route expansion follows USPS Appendix F. Repeated equivalent suffixes are treated as possible feed artifacts, while the literal name is retained because consecutive suffix words can be part of a registered street name under USPS section 234.

Recorded property-line scoring checks house number, street name, suffix and both directionals. It deliberately does not score units, since `PROPERTYADDRESSFULL` sometimes omits the separately stored unit. Untouched MLS listing-string scoring checks those fields plus the unit, including when the listing string omits or contradicts it. That second metric therefore mixes parser coverage with agreement between source fields.

Generated cases are constructed from the observed structured house/street/unit fields. The explicit variant includes the source unit prefix or `UNIT`; the bare variant omits that prefix; the full variant adds city/state/ZIP. These are generated formatting tests based on real records, not raw MLS strings. Expected suffix names use an independent USPS primary-name reference in `scripts/usps-suffix-reference.json`; directionals and case/whitespace normalize consistently for both builds.

No held-out scenario lost a match previously found by the baseline. Development scoring still loses a few baseline matches to malformed source inputs, such as a dangling slash in a house identifier or a bare hash with no secondary identifier. Those cases remain diagnosed instead of being admitted merely to raise a score.

## API migration and operational limits

`AddressComponents` is now a union. Street candidates retain the existing runtime shape with an omitted `kind`; non-street kinds have no fabricated house/street fields. Code extending the old interface or assuming those fields always exist must migrate to `StreetAddressComponents` or narrow on `kind`. House/street spans are now optional.

Adapters must match `secondaryUnits` in full when present. The singular `secondary` is the last component in input order, not necessarily the apartment, and cannot establish building identity by itself. Candidate IDs are opaque; old counts and spellings are not stable application contracts. Broader candidates may cause a resolver to report legitimate ambiguity where an earlier release returned a single match.

Fixed limits are 4,096 characters per field, 128 tokens and 256 candidates. Exceeding a limit yields no candidates and does not query the index. They bound resource use at the cost of rejecting unusually long or highly ambiguous inputs. Corpus runs did not require raising these limits.

Unsupported or partly represented inputs include intersections, recipient/company blocks, dual street-and-PO-box blocks, kilometer-only Puerto Rico rural descriptions, unnumbered properties, and arbitrary malformed listing prose. Puerto Rico urbanization and military formats have synthetic format tests; this corpus does not provide territorial or overseas validation. Fuzzy correction, missing-component inference, postal deliverability and city/ZIP validity require an external source. Literal fallback can retain unsupported text, so candidate existence is not a validity flag.

The corpus comparison does not measure false positives or end-to-end matching accuracy. A broader candidate set can increase recall and lookup cost. Only an authoritative index and separately labeled matches/nonmatches can establish resolution accuracy. No production resolution claim is made from these parsing measurements.
